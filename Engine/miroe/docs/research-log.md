# miroe 연구 기록 (상세)

miroe는 이미 문제를 풀고 있는 오픈소스 프로젝트들의 결과를 합친 **연구용 통합 엔진**이에요. 그 위에서 아직 아무도 풀지 못한 고수준 문제를 연구해요.

**방향 (2026-11-27, 사용자 확정)**: miroe는 애플 실리콘 전용 ARM64 네이티브 Wine + FEX 엔진이에요. 모든 연구와 최적화는 ARM64 네이티브 엔진에서 하고, x86_64 엔진은 비교 대조군으로만 써요. 기반 구성은 [base.md](base.md)에 있어요.

- **기반(ARM64 Wine + FEX + DXMT)은 성과가 아니에요.** MetalSharp, Hadron이 이미 해 놓은 걸 라이선스를 지켜 가져와요. 직접 다시 만들지 않아요.
- **성과는 기반 위에서 측정한 실제 병목을 구조적으로 개선하는 것**이에요. 패치 개수보다 파급력과 검증 가능한 숫자를 우선해요.
- 어떤 기술도 "세계 최초"라고 하지 않아요. 독창성은 구체적인 구현과 측정 결과로 판단해요.

2026-11-27에 각 저장소, 이슈 본문, 기여 정책을 직접 확인했어요.

**규칙**
- 가져온 패치마다 첫머리에 출처(프로젝트, 원래 작성자, 커밋, 라이선스)를 적어요.
- Miro는 GPL-3.0이라 LGPL, MIT, BSD, zlib 코드를 함께 배포할 수 있어요. AGPL 코드는 넣지 않아요.

## 2. 구조

Hadron 방식을 따라가요. 업스트림 소스는 커밋으로 고정하고, 우리 변경은 컴포넌트별 패치로만 둬요.

```
Engine/miroe/
  sources.conf          업스트림 저장소와 고정 커밋
  patches/<컴포넌트>/   NNNN-설명.patch (출처 머리말 포함)
  scripts/              fetch, build-wine, build-fex, build-dxmt, package
  tools/                profile.sh, memwatch.sh, frame-breakdown.py
  prefix/               C: 드라이브 설정 (cjk-fonts.py)
```

빌드와 실험은 **`/Users/Shared/miroe-lab`** 에서만 해요. 경로가 짧아야 Wine이 안전해요. Miro의 엔진과 C: 드라이브(사용자 데이터)는 건드리지 않아요.

## 3. 연구 과제

### 1순위: Apple Silicon 통합 메모리 관리 (MUMA, 가칭)

- **문제**: [DXMT #260](https://github.com/3Shain/dxmt/issues/260) (Open, PR 없음). Deadlock에서 큰 `WRITE_DISCARD` 업로드가 몰린 뒤 스테이징 블록 큐가 줄어들지 않아요. 작성자는 GPU 메모리가 1.5GB에서 7.2GB까지 늘었고, 자신의 수정으로 35분 동안 1.3~1.9GB를 유지했다고 보고했어요.
- **재현 (2026-11-27)**: `Engine/tests/d3d11-memory-test.cs`(중립 테스트, 화면 없음)와 `tools/memwatch.sh`로 실습실 DXMT v0.80에서 재현했어요. v0.80과 지금 main의 할당기 파일은 같아요.

  | | 유휴 GPU 메모리 |
  | --- | ---: |
  | 몰아치기 없음 (대조군) | 5MB |
  | 32MB보다 큰 discard 600프레임 뒤, 조용한 구간 3000프레임 | **920MB** (줄지 않음) |

- **연구 방향**: 작성자의 수정을 기준선으로 삼고, 그보다 나은 구조를 찾아요.
  - macOS 메모리 압력 알림에 따라 할당 정책 바꾸기
  - GPU 작업 완료 시점 기준 회수
  - 크기별 풀
  - 남는 블록을 Metal의 purgeable 상태로 두기
  - `MTLHeap`, `MTLResidencySet` 활용
  - 통합 메모리에서 복사 없는 업로드 경로
- **측정**: 같은 테스트로 최대치·유휴 메모리·프레임 시간을 비교해요. 게임별 패턴은 중립 테스트로 흉내 내요.

#### 결과: MUMA v0 (2026-11-27)

**원인** (DXMT 소스 `src/dxmt/dxmt_dynamic.cpp`): `WRITE_DISCARD`를 할 때 GPU가 아직 옛 메모리를 쓰고 있으면, `DynamicBuffer`가 버퍼 크기만큼 새 블록을 받아요. 옛 블록은 재사용 대기열에 들어가는데, 이 대기열은 줄어들지 않아요. 그래서 몰아치기 동안 동시에 쓰인 블록 수 × 버퍼 크기가 버퍼가 살아 있는 동안 계속 남아요. 제보자의 수정은 그 버퍼가 다시 쓰일 때만 대기열을 줄여서, 몰아치기 뒤 쉬는 버퍼의 메모리는 그대로 남아요.

**MUMA v0** ([`patches/dxmt/0001`](../patches/dxmt)):
- 명령 큐(장치)마다 예비 블록을 가진 동적 버퍼의 목록을 둬요.
- GPU 완료를 기다리는 스레드가 16번 완료마다 300회 이상 쓰이지 않은 예비 블록을 풀어요.
- 시퀀스 번호가 큐마다 달라서 목록도 큐마다 따로 둬요. 장치가 여럿이어도 쓰는 중인 메모리를 풀지 않아요.

ARM64 Wine 11.22 + FEX + DXMT(Hadron 기준), M4 Pro, `Engine/tests/c/d3d11-memory-test.c`(600프레임 몰아치기 → 3000프레임 조용히):

| DXMT | 몰아치기 뒤 GPU 메모리 | 몰아치기 속도 (3회 평균) |
| --- | ---: | ---: |
| 원래 | 920MB | 1.462ms/프레임 |
| A: #260 제보자 수정 ([`patches/experiments`](../patches/experiments)) | 920MB | 1.466ms/프레임 |
| **B: MUMA v0** | **312MB** (약 2초 안에 회복) | 1.463ms/프레임 |

- 312MB는 테스트가 실제로 쓰는 버퍼 크기예요(40+48+64MB × 동적·기본 2벌). **쓰는 만큼만 남았어요.**
- 64비트 테스트를 FEX로 돌려도, ARM64로 바로 돌려도 같아요.
- 속도 차이는 측정 오차 안이에요.

#### 결과: MUMA v1 (2026-11-27)

v0에서 남은 빈틈 두 개를 테스트로 먼저 확인했어요. 하나는 제출을 멈춘 앱에서 회수가 돌지 않는 것, 다른 하나는 동적 2D 텍스처가 v0가 다루지 않는 `DynamicLinearTexture` 경로로 간다는 것이에요.

**MUMA v1** ([`patches/dxmt/0002`](../patches/dxmt), v0 위에 적용):
- 동적 버퍼와 동적 텍스처가 같은 기반(`DynamicSpareHolder`)과 큐별 목록을 써요.
- 명령 큐마다 회수 스레드가 0.25초마다 돌아요. GPU가 다 썼고 2초 지난 예비 블록을 풀어요. 그래서 제출이 멈춰도 회수돼요.
- 1MB 이상 버퍼의 예비 블록은 GPU가 다 쓰자마자 purgeable(volatile)로 표시하고, 다시 쓸 때 원래대로 돌려요. winemetal에 `MTLResource_setPurgeableState`(유닉스 호출 146)를 더했어요.
- 이미 등록된 경우에는 등록을 잠금 없이 해요(원자 플래그). 큐가 비었을 때만 그 리소스의 잠금 안에서 플래그를 지워요.
- 측정용 스위치: `MIROE_MUMA_FREE_MS`, `MIROE_MUMA_PURGEABLE=0`

| 경우 (몰아치기 뒤) | 원래 | v0 | **v1** |
| --- | ---: | ---: | ---: |
| 동적 버퍼, 제출 계속 | 920MB | 312MB | **308MB** |
| 동적 버퍼, 제출 멈춤 | 920MB | 920MB | **308MB** (약 3초) |
| 64MB 동적 텍스처 | 968MB | 968MB | **200MB** (약 2초) |

purgeable만 따로 잰 결과예요(예비 블록을 60초 유지, 조용한 구간).

| | 메모리 사용량 | GPU dirty | 회수 가능 |
| --- | ---: | ---: | ---: |
| purgeable 끔 | 1,025MB | 920MB | 0.8MB |
| **purgeable 켬** | **417MB** | **312MB** | **609MB** |

예비 블록은 재사용할 수 있게 남겨 두면서, 앱의 메모리 사용량에서는 빠지고 OS가 필요하면 가져가요.

| 속도 (3회 평균) | 원래 | v0 | v1 | v1, purgeable 끔 |
| --- | ---: | ---: | ---: | ---: |
| 큰 버퍼 몰아치기 (ms/프레임) | 1.511 | 1.556 | 1.533 | 1.511 |
| 작은 discard 2000번 (ms/프레임) | 3.204 | 3.308 | **3.220** | 3.141 |

- 차이는 측정 오차 안이에요. 큰 버퍼 값은 0.1초 단위로 재서 해상도가 0.033ms예요.
- v0의 등록 잠금 비용(작은 discard +3%)은 v1의 잠금 없는 등록으로 없어졌어요.
- **데이터 확인**: purgeable 상태였다가 재사용된 블록으로 1MB 패턴을 8번 쓰고 GPU 복사 후 읽어 보니 모두 정확했어요. 원래 엔진, v1(예비 블록 유지 / 2초 회수), x64(FEX)에서 모두 확인했어요.

#### 게임 비슷한 테스트 (2026-11-27)

실제 게임은 쓰지 않고, #260의 Deadlock 업로드 패턴을 흉내 낸 중립 프로그램 `Engine/tests/c/d3d11-game-test.c`로 쟀어요(창 없음).
- **매 프레임**: 그리기 명령 1,500~3,000번. 그리기마다 상수 버퍼 discard, 파티클 정점 버퍼는 NO_OVERWRITE 링, 1920×1080 렌더 타깃.
- **교전**: 큰 동적 버퍼 36·40·64MB를 매 프레임 discard하고, 10프레임마다 텍스처에 36MB를 `UpdateSubresource`로 올려요.
- **조건**: 최대 3프레임 대기, 120fps 제한.
- **흐름**: 준비 5초 → 평상시 20초 → 교전 10초 → 평상시 20초 → 교전 10초 → 메뉴 15초

ARM64 Wine + FEX + DXMT, 경우마다 3번 실행한 평균(± 범위의 절반). 측정 중 Mac이 잠든 4번은 빼고 다시 돌렸어요. `scripts/game-matrix.sh`는 이제 `caffeinate -i`로 측정하는 동안만 잠들지 않게 해요.

| 메모리 (단계 끝, MB) | 교전 1 뒤 (GPU) | 교전 2 뒤 메뉴 (GPU) |
| --- | ---: | ---: |
| 원래 | 923 (582) | 1,054 (722) |
| A: 제보자 수정 (1회) | 927 (586) | 1,055 (722) |
| **v1** | **644 (302)**: −30% | **627 (294)**: −41% |
| v1, 예비 블록 30초 유지 | 645 (302) | 627 (294) |

| 프레임 시간 (ms) | 교전 1 평균 / p99 | 교전 2 평균 / p99 / 최대 | 평상시 2 p99 |
| --- | --- | --- | --- |
| 원래 | 1.21 / 6.25 | 1.82 / 10.59 / 13.0 | 1.36 |
| **v1** | 1.19 / 6.06 | 1.80 / 10.26 / 12.0 | 1.30 |
| v1, 30초 유지 | 1.21 / 6.43 | 1.81 / 10.52 / 12.6 | 1.32 |

- **교전이 끝나면 메모리가 돌아와요.** GPU 메모리는 48~59% 줄었어요.
- **제보자 수정은 이 패턴에 효과가 없었어요.** 교전이 끝나면 큰 버퍼를 더 매핑하지 않아서, 그 수정의 회수 조건이 오지 않아요.
- **프레임 시간 차이는 실행마다의 범위 안이에요.** v1이 회수한 메모리를 다시 할당해야 하는 교전 2 시작에서도 끊김이 보이지 않았어요(교전 2 p99 범위 ±1.3ms).
- 교전 중 최대 메모리는 세 경우 모두 비슷해요(1,045~1,226MB). **MUMA는 교전 중 최대치를 낮추지 않고, 교전 뒤에 돌려줘요.** 한 번 30초 유지가 더 낮게 나왔지만 반복하니 사라졌어요.
- 이 DXMT 버전에서는 #260 1부(스테이징 할당기의 "forced to allocate" 경고)가 나오지 않았어요(모든 실행에서 0건). 남은 건 MUMA가 다루는 동적 버퍼 문제예요.
- 30초 유지 설정은 메모리 사용량이 2초 회수와 같았어요(purgeable 덕분). 하지만 이 테스트에서는 속도 이득도 보이지 않았어요.

#### 결과: MUMA v2, DXVK 참고 (2026-11-27)

**MUMA v2** ([`patches/dxmt/0003`](../patches/dxmt), v1 위에 적용)는 [DXVK](https://github.com/doitsujin/dxvk)(zlib) 메모리 할당기의 검증된 정책을 더했어요. DXVK 코드를 복사하지 않고, 정책을 DXMT 구조에 맞게 다시 구현했어요. 코드 주석에 DXVK 파일과 함수 이름을 적었어요.

| | 어디서 | 내용 |
| --- | --- | --- |
| 가져온 것 | DXVK `src/dxvk/dxvk_memory.cpp` `freeEmptyChunksInPool` | 유휴 메모리 한도. DXVK는 mapped 메모리를 최대 크기 청크 4개(4×256MB)까지 둬요. 우리는 `min(1GB, 예산/8)` |
| 가져온 것 | 같은 파일 `updateMemoryHeapBudgets` | 예산 = Metal `recommendedMaxWorkingSetSize` − 1%(4~256MB). 예산을 넘으면 유휴 예비 블록을 모두 풀고, 새 할당 전에 `makeRoom()`이 먼저 자리를 만들어요 |
| 가져온 것 | 같은 파일 (한 번에 청크 하나) | 시간 규칙은 한 번에 최대 256MB만 풀어요 |
| MUMA 고유 | | 제출과 상관없는 회수 스레드(DXVK의 timed task는 제출 직후에만 돌아요, `dxvk_queue.cpp`), purgeable, 잠금 없는 등록, 동적 텍스처, 2초 규칙 |

측정용 스위치: `MIROE_MUMA_MAX_IDLE_MB`, `MIROE_MUMA_BUDGET_MB`(작은 Mac 흉내). 이 Mac(M4 Pro 24GB)의 예산은 18,004MB예요. 스크립트: [`scripts/v2-matrix.sh`](../scripts/v2-matrix.sh), [`scripts/v2-report.py`](../scripts/v2-report.py).

**회귀 (v1과 같아야 함)**: 버퍼 308MB, 제출 멈춤 308MB, 텍스처 196MB(GPU 메모리). 재사용 데이터 확인 통과. 작은 discard 3.243ms/프레임(v1 3.262).

**게임 비슷한 테스트** (경우마다 3번, 모두 유효)

| | 교전 1 뒤 / 메뉴 (MB) | 교전 중 최대 1 / 2 (MB, 평균) | 교전 2 최대의 범위 | 교전 1 평균 / p99 (ms) | 교전 2 평균 / p99 / 최대 (ms) |
| --- | --- | --- | --- | --- | --- |
| v2, 기본 예산 | 645 / 629 | 1,116 / 1,193 | 1,052~1,334 | 1.20 / 6.77 | 1.60 / 8.40 / 11.0 |
| v1, 예산 800MB 흉내 | 645 / 627 | 1,094 / 1,213 | 1,046~1,365 | 1.17 / 6.31 | 1.47 / 8.25 / 11.0 |
| **v2, 예산 800MB 흉내** | 649 / 634 | **1,061 / 1,156** | **1,153~1,157** | 1.23 / 6.51 | 1.60 / **7.88 / 10.1** |

- 기본 예산에서는 v2가 v1과 같아요. 큰 Mac에서는 예산 규칙이 끼어들 일이 없어요.
- 예산 800MB에서는 교전 중 최대치가 평균 3~5% 낮아졌고, **실행마다 튀던 최대치(최대 1,365MB)가 1,157MB 안으로 고르게 묶였어요.**
- 대가는 보이지 않았어요. 프레임 시간 차이는 실행마다의 범위 안이에요.
- 교전 중 최대치의 대부분은 지금 쓰는 메모리라서, 회수 정책으로는 더 줄일 수 없어요. 작은 Mac(8GB 등)에서 실제 메모리 압력 아래 확인은 남아 있어요.

**남은 일**
- 실제 게임 패턴 테스트는 위처럼 첫 버전이 생겼어요. 더 다양한 엔진의 업로드 패턴(Unity, Unreal)을 더해야 해요.
- purgeable을 텍스처에도 적용해야 해요. 버퍼 위에 만든 선형 텍스처라서 밑의 버퍼에 걸어야 해요.
- 32비트의 직접 할당(placed) 메모리는 `madvise`로 처리해야 해요(#161과 같이).
- 메모리 압력 아래에서 purge가 실제로 일어날 때의 동작을 확인해야 해요.
- 예비 블록을 오래 두는 설정(예: 10초)과 재할당 비용 사이의 균형도 재 봐야 해요.

### 2순위: 그래픽 명령 처리 구조

- **문제**: [DXMT #204](https://github.com/3Shain/dxmt/issues/204) (Open). DEFAULT 상수 버퍼에 `UpdateSubresource`를 할 때 그 버퍼가 **픽셀 셰이더에 묶여 있으면** 비용이 그리기 횟수의 제곱으로 늘어요. 그리기 24,000번에서 DXMT 87.29ms, D3DMetal 12.17ms예요(같은 실행 파일, M3 Max). ARM64 + FEX에서도 같다고 보고돼 있어서 ARM64 전환으로는 해결되지 않아요.
- **연구 방향**: 먼저 관련 수정이 있는지 확인해요(이슈에 댓글이 없어서 아직 못 찾았어요). 그다음 픽셀 셰이더에서만 생기는 이유와 제곱이 되는 근본 원인(버퍼 버전 관리, 인자 버퍼 재인코딩)을 DXMT 소스와 Metal 쪽 측정으로 찾아요.

### 4순위: 가상 메모리와 Metal

- **문제**: [DXMT #161](https://github.com/3Shain/dxmt/issues/161) (Open, DXMT 개발자 직접 등록). 32비트 프로세스는 DEP가 기본으로 꺼져 있어서 Wine이 메모리에 실행 권한을 주는데, Tahoe 이후 Metal이 그런 메모리를 아주 느리게 다뤄요. Metal HUD는 55~76 FPS인데 실제 `Present()`는 초당 약 5번이에요.
  - 피해 게임: Aokana, Mahjong Soul 등 32비트 Unity. **Miro 사용자층과 겹쳐요.**
  - 우회책: PE 헤더에 `NX_COMPAT`를 넣는 방식이 있어요.
- **연구 방향**: DXMT 개발자가 제시한 방향이에요. 프로세스 전체 DEP 정책을 바꾸지 않고, DXMT가 Wine을 통해 할당하는 placed buffer 메모리만 실행 불가로 만들어요. Wine의 32비트 주소 관리(WoW64)와 같이 봐야 해요.

Mullion 원래도 DXMT와 같이 예비 블록을 회수하지 않아서 #260이 그대로였고(923MB), 이식판은 DXMT판과 같은 결과예요(308MB, 텍스처 199MB, 게임형 테스트에서 GPU −48~53%). #### 결과: W1, DEP가 꺼진 32비트 프로그램의 지연 실행 권한 (2026-11-27)

> **Intel Wine + Rosetta에서의 독립 연구 성과로 보존해요.** Miro 1.2의 x86_64 엔진에는 넣지 않아요. ARM64 네이티브에서는 W^X 때문에 같은 조건(쓰기+실행 메모리 위의 Metal 버퍼)이 생기지 않을 것으로 보고, 실제 32비트 확인은 서명 권한이 생긴 뒤에 해요. 문제가 없으면 이 패치는 miroe에 넣지 않아요([base.md](base.md) 4장).

[problems.md](problems.md)의 조사에서 아직 풀리지 않은 문제 중 파급력이 가장 큰 과제로 골랐어요. 측정은 모두 Rosetta 경로(Intel용 Wine 11.21 Staging + DXMT v0.80, macOS 27.2, M4 Pro)이고, 중립 테스트 프로그램만 썼어요.

**1. 재현.** `Engine/tests/c/d3d11-game-test.c`를 32비트로 빌드하고 `NX_COMPAT` 표시만 다르게 한 두 파일로 쟀어요(20초).

| | 프레임 수 | 프레임 시간 |
| --- | ---: | --- |
| `NX_COMPAT` 있음 | 2,160 | 평상시 1.3ms |
| `NX_COMPAT` 없음 | 37 | 약 1.25초짜리 멈춤이 계속 |

macOS 27.2에서도 그대로예요(이슈에서 "macOS 27에서 고쳐졌는지" 묻는 댓글이 있었어요). 멈춤 길이는 이슈 댓글의 측정(1.15~1.25초)과 같아요.

**2. 원인 분리 (Wine 없이).** [`tools/w1/`](../tools/w1)의 작은 Mac 프로그램을 x86_64로 빌드해서 Rosetta에서 돌렸어요.
- CPU만 쓰면 쓰기+실행 메모리도 보통 메모리와 같은 속도예요(64MB 첫 쓰기 9ms). 페이지 첫 접근 비용이 원인이 아니에요.
- **그 메모리 위에 Metal no-copy 버퍼를 만들고 GPU가 쓰면, 다음 CPU 접근이 약 1.1~1.25초 멈춰요.** 버퍼 크기(1~32MB)와 상관없이 버퍼마다 한 번이에요. 실행 권한이 없으면 0.03ms예요.
- 실행 권한이 없는 코드 페이지를 실행하면 Rosetta가 fault를 내고, 그때 실행 권한을 주면 이어서 실행돼요. 지연 실행 권한이 가능한 근거예요.

**3. Wine 안에서 확인.** 연구용 훅(`tools/w1/w1-hook.m`, 출시용 아님)으로 DXMT가 만드는 no-copy 버퍼를 지켜봤어요.
- `NX_COMPAT` 없음: placed 버퍼 452개가 **모두** 실행 가능한 메모리 위에 있었어요. 있음: 0개.
- 버퍼를 만들기 직전에 그 메모리의 실행 권한만 빼면 1,997프레임(정상)이 됐어요. 반대로 페이지를 미리 만져 두는 방법은 작은 프로그램에서는 통했지만 Wine 안에서는 효과가 없었어요(35프레임). DXMT 쪽 실험 커밋으로 남겨 뒀어요.

**4. 해결: Wine의 지연 실행 권한** ([`patches/wine-x86_64/0001`](../patches/wine-x86_64))
- DEP가 꺼져도 미리 모든 페이지에 `PROT_EXEC`를 붙이지 않아요. 읽을 수 있는 페이지에서 **처음 실행 fault가 나면 그 페이지에만** 실행 권한을 주고 다시 실행해요.
- Rosetta는 명령어 가져오기를 읽기 fault로 알릴 수 있어서, macOS에서는 fault 주소가 명령어 포인터에서 16바이트 안이면 실행 fault로 봐요. 이미 실행 가능한 페이지면 건너뛰어요(무한 반복 방지).
- DEP를 다시 켜면 지연으로 받은 실행 권한을 거둬요. macOS에서 기본으로 켜지고, `WINE_LAZY_EXEC=0`이면 원래 동작이에요.
- DXMT만이 아니라 같은 메모리를 쓰는 DXVK와 다른 프로그램에도 적용돼요. 3Shain이 말한 "DXMT의 placed 메모리만 실행 불가로"보다 넓은 해결이에요. DXMT 쪽 변경은 필요 없어요.

| 32비트 게임형 테스트 (20초, 3회) | `NX_COMPAT` 없음 | `NX_COMPAT` 있음 |
| --- | ---: | ---: |
| 원래 Wine | 35프레임 | 2,062프레임 |
| 같은 빌드, `WINE_LAZY_EXEC=0` | 31 | 2,056 |
| **지연 실행 권한** | **1,997** | 1,990 |

| 프레임 시간 (ms) | 평상시 평균 / p99 | 교전 평균 / p99 |
| --- | --- | --- |
| 원래 Wine, `NX_COMPAT` 있음 | 1.47 / 1.74 | 3.15 / 10.57 |
| **지연 실행 권한, `NX_COMPAT` 없음** | 1.49 / 1.75 | 3.18 / 10.66 |

- **정확성**: [`Engine/tests/c/dep-off-exec-test.c`](../../tests/c/dep-off-exec-test.c)의 9가지 경우를 각각 따로 실행했어요. VirtualAlloc·힙·malloc·.data·스택에서 코드 실행, 실행한 뒤 고쳐 쓴 코드, 페이지 경계에 걸친 명령어, VirtualProtect 뒤 실행이에요. 원래 Wine과 같이 모두 통과했고, DEP가 켜진 빌드에서는 모두 막혔어요(Windows와 같아요).
- **64비트**는 영향이 없어요(작은 discard 3.345 / 3.341ms).
- **남은 것**: ARM64 + FEX 엔진에서 32비트 프로그램으로 같은 문제가 없는지 확인(서명 권한이 생긴 뒤). x86_64 엔진에는 옮기지 않아요
- 스크립트: [`scripts/w1-matrix.sh`](../scripts/w1-matrix.sh), [`scripts/w1-depexec.sh`](../scripts/w1-depexec.sh), [`scripts/w1-report.py`](../scripts/w1-report.py)

## 4. 정책

- **DXMT에는 AI가 만든 코드를 PR로 내지 않아요.** DXMT의 [기여 정책](https://github.com/3Shain/dxmt/blob/main/CONTRIBUTING.md)은 AI/LLM이 만들었거나 같이 만든 기여를 받지 않아요. AI로 한 연구 결과와 재현 자료를 공유하는 건 허용해요(PR이 아닌 이슈·댓글로).
- 결과를 공유할 때는 짧고 확인 가능한 내용만 써요. DXMT 개발자는 AI가 덧붙인 장황한 "근거" 부분을 보고서를 읽기 어렵게 만드는 잡음이라고 했어요(#200).
- Wine에 코드를 넣으려면 실명이 필요해요. 하게 되면 그때 따로 정해요.
- 사용자 게임은 테스트에 쓰지 않아요. 중립 테스트 프로그램만 쓰고, 창은 화면 밖에 둬요.
- Miro의 기존 엔진과 사용자 데이터는 건드리지 않아요.
